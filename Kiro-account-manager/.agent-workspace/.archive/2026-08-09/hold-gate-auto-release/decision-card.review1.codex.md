# 第 1 轮评审结论

## 一、原始用户目标与可观察成功状态

文档给出的原始目标来源明确：

- **角色**：使用 Claude Code / SUB、通过反代等待账号恢复的用户。
- **操作**：账号不可用时请求进入挂起；开启自动放行；通过桌面界面观察下一次放行和累计次数。
- **期望结果**：请求越过客户端约 10 分钟的看守窗口，账号恢复后正常完成。
- **负向条件**：不能只出现定时器或日志活动，而客户端请求仍在约 10 分钟处终止。

但当前成功状态**尚未形成可信闭环**：文档同时声称“放行后会产生真实正文重置客户端计时器”，又在状态机中写明“仍无号 → 重新 enterHold”，该路径没有生成任何正文。核心因果关系自相矛盾。

## 二、端到端 Goal→Outcome 链路表

| 跳 | Producer | Artifact | Consumer | 消费后结果 | 失败行为 |
|---|---|---|---|---|---|
| 1 | 用户、桌面配置控件 | 自动放行开关、间隔 | IPC 配置更新及持久化 | 配置写入并热生效 | `HOLD_KEYS` 漏键时界面显示已改、运行时不生效 |
| 2 | `runWithHold` | 挂起条目 | `HoldGate` | 集合非空后启动自动放行 timer | timer 未启动、重复启动或集合空后未停止 |
| 3 | 自动放行 timer | `releaseAll()` 调用及 resume | `runWithHold` 主循环 | 挂起请求重新进入选号流程 | 并发手动放行、超时或自动放行竞争时只能有一个消费者成功 |
| 4 | `runWithHold` / `pickFresh()` | 新的上游尝试或再次挂起 | 上游服务、客户端响应流 | 有可用号时产生真实正文；无号时再次挂起 | **文档未证明无号场景会产生客户端可见字节，因此无法证明看守被重置** |
| 5 | `HoldGate` getters | 下一次放行时间、累计次数等状态 | `ProxyServer`、IPC、推送事件 | 桌面端和手机端显示状态 | 两个发射点形状不一致时，字段时有时无 |

| 7 | 上游恢复 | 真实响应正文 | Claude Code / SUB | 请求继续并最终完成 | Layer C 若先触发首字节超时，请求会在下一次自动放行前失败 |

**结论**：第 3→4→客户端看守重置这一关键跳尚未成立，是当前 P0 断链。

## 三、主要评审问题

### A1 — P0｜架构级：自动放行与“真实正文续接”之间存在核心因果断链

- **定位锚点**：`### 状态机（自动放行循环 · 已核对现有主循环）`
- **问题**：成功状态称 `releaseAll()` 后“重跑上游吐出的真实正文”会重置客户端计时器；状态机却明确给出“仍无号 → 重新 enterHold”，期间没有上游正文。
- **问题根因**：把“唤醒挂起 Promise、重新执行选号”直接等同于“客户端收到语义正文字节”。
- **业务影响**：功能可能定时正常、计数正常、日志正常，但客户端仍在原看守窗口处终止，用户核心目标完全未实现。
- **架构影响**：当前调度器位于 HoldGate 层，但目标约束发生在客户端响应流层；二者之间缺少已证明的有效机制。
- **修改建议**：开工前先锁定一个“池始终无可用号”的样本，证明自动 `releaseAll()` 后客户端实际收到哪些字节、何时收到、为何能重置计时器。若没有客户端可见的有效正文，应停止在 HoldGate 下游补 timer，重新选择能够真正影响响应流的责任层。
- **优先级**：**P0**

### A2 — P1｜功能闭环：链路表以文件接线为主，缺少每跳产出、结果和失败行为

- **定位锚点**：`### 配置链路 7 节点（生产者 → 消费者 · 来源：recon §3.1，逐条已核）`
- **问题**：现有表只描述配置字段和文件消费者，没有覆盖挂起条目、timer 触发、CAS 认领、主循环重入、上游正文、客户端看守重置的完整运行时链路。
- **问题根因**：将“文件需要修改”当成了“生产行为已经闭环”。
- **业务影响**：可能所有任务均完成，但关键产出没有正确消费者，形成“代码接好但用户结果未发生”。
- **架构影响**：无法审核 producer/consumer 是否一一可达，也无法识别错误消费者。
- **修改建议**：补充运行时 Goal→Outcome 表，每跳明确 producer、artifact、consumer、消费后状态及失败行为，并把客户端实际收到正文作为最终一跳。
- **优先级**：**P1**

### A3 — P1｜架构级：已知 Layer C 时间冲突被悬置为“谁后落地谁负责”

- **定位锚点**：`### ⚠️ 时间常数约束（与并行会话 \`proxy-context-safety-net\` 的接线）`
- **问题**：文档已经确认 480 秒自动放行与 200 秒首字节超时不兼容，却未形成统一真源、注册门禁或明确责任人。
- **问题根因**：跨功能不变量仅留在两份文档约定中，没有进入可执行契约。
- **业务影响**：两个功能分别通过测试后，组合到生产仍会在 200 秒终止。
- **架构影响**：时间常数成为跨模块隐式耦合，后落地者容易漏读本卡。
- **修改建议**：在开工方案内明确唯一时间约束所有者、兼容公式、配置变更校验及组合测试；不能以“谁后落地谁负责”作为闭环。
- **优先级**：**P1**

### A4 — P1｜架构级/业务现实：手机端新增写接口缺少业务必要性与安全契约

- **定位锚点**：`- [ ] T-5 手机面板：扩 \`PanelProxyStatus\` 三个可选字段 + \`POST /api/proxy/release-held\``
- **问题**：用户来源只明确要求显示下一次放行和累计次数，未说明必须新增手机端手动放行接口；该写接口也未定义鉴权、租户/实例范围、输入输出、稳定错误码和重放行为。
- **问题根因**：把手机面板存在展示需求扩展成了新的写能力，存在 Solution-Jumping。
- **业务影响**：无依据扩大改动面；若接口可远程触达，还可能导致非授权放行或错误实例被操作。
- **架构影响**：新增第二种放行传输入口，但尚未证明最终仍收口到同一领域命令和权限边界。
- **修改建议**：补充具体操作角色、缺失影响、现有手动放行机制是否覆盖、A/B/C/D 分类；若无法证明业务必要性则删除。若保留，必须补齐权限、实例范围、响应、错误、并发和审计契约。代码事实需实现方核实。
- **优先级**：**P1**

### A5 — P1｜契约级：预算、绝对 deadline 与自动放行的语义互相冲突

- **定位锚点**：`| D2 | 预算耗尽（\`keep_blocking\` 下留在集合）的条目是否继续自动放行`
- **问题**：文档同时规定绝对 deadline 不重置、预算耗尽后继续自动放行、界面称“覆盖预算上限”，并将间隔 clamp 到 `holdTotalBudgetMs`。这些规则没有形成一致的状态语义。
- **问题根因**：未区分“预算限制何种行为”“deadline 到达后条目处于什么状态”“覆盖预算是覆盖等待、重试还是超时结论”。
- **业务影响**：用户可能认为预算已失效，但系统仍执行 timeout；或配置区间在预算小于 60 秒时无法满足。
- **架构影响**：状态机存在两个相互竞争的时间真源。
- **修改建议**：明确 deadline 后的合法状态、自动放行是否仍可认领、总预算约束对象，以及 `holdTotalBudgetMs < 60000`、零值和禁用值的归一化规则。
- **优先级**：**P1**

### A6 — P1｜接口契约：读数形状及空值语义未封闭

- **定位锚点**：`### 读数链路（倒计时 + 累计次数）`
- **问题**：正文只命名 `nextAutoReleaseAt` 和 `autoReleaseCount` 两项，但任务 T-5 要扩“三个可选字段”；第三字段未定义。关闭、空集合、timer 重建、反代停止时 `nextAutoReleaseAt` 的值也未约定。
- **问题根因**：UI 展示需求尚未转化为稳定的跨进程数据契约。
- **业务影响**：桌面端和手机端可能分别猜测 `undefined`、`null`、`0` 的含义，产生错误倒计时或错误开启状态。
- **架构影响**：IPC、事件推送和手机 API 可能形成多套状态定义。
- **修改建议**：钉死完整字段集合、类型、空值、关闭态、停服态、重建 timer 后的时间戳语义，以及计数是“周期次数”还是“条目数”。
- **优先级**：**P1**

### A7 — P1｜决策完整性：未比较沿用现状、局部调整与边界调整

- **定位锚点**：`### 三项主 AI 裁决（已定，理由留痕）`
- **问题**：文档只比较了 timer 实现细节，没有比较继续手动放行、HoldGate 自动唤醒、响应流层续接等方案。
- **问题根因**：在验证核心机制前已跳到 `releaseAll()` 调度器方案。
- **业务影响**：可能以最低实现成本选择了无法实现用户结果的方案。
- **架构影响**：缺少当核心因果实验失败时的停止条件和替代边界。
- **修改建议**：比较沿用现状、局部增加自动唤醒、调整到真正控制客户端响应的边界，说明收益、成本、风险、可逆性及停止条件。
- **优先级**：**P1**

### A8 — P1｜验证级：生产场景没有锁定最关键的失败窗口和组合行为

- **定位锚点**：`### 最终 sink + 真跑一次的 e2e 姿势`
- **问题**：当前 e2e 只写了最终操作步骤，没有明确记录客户端在每个放行周期实际收到的内容、看守截止时间是否被重新计算，也没有纳入 Layer C 组合场景。
- **问题根因**：验证仍偏最终“是否完成”，没有对核心因果链逐跳取证。
- **业务影响**：一次账号恰好恢复的成功可能掩盖自动放行本身无效。
- **架构影响**：无法区分“账号恢复导致成功”与“自动放行延长了客户端存活时间”。
- **修改建议**：至少推演并验收：持续无号跨越 10 分钟、间隔热更新、手动/自动/超时并发、Layer C 启用四种场景；分别记录客户端可见字节、时间点和最终状态。
- **优先级**：**P1**

## 四、断链、孤儿产出与错误消费者清单

1. **关键断链**：`releaseAll()` → 主循环重入 → 客户端收到语义正文，目前缺少中间产出。
2. **潜在孤儿产出**：`nextAutoReleaseAt`、`autoReleaseCount` 的事件字段虽计划产生，但完整形状和空值语义未确定。
3. **潜在错误消费者**：两个 `onHeldRequestsChanged` 发射点若形状不同，桌面消费者会收到不稳定契约。
4. **悬空跨模块约束**：Layer C 与自动放行的时间关系没有唯一所有者。
5. **范围可疑产出**：手机端新增 `POST /api/proxy/release-held` 尚未证明来自真实业务需求。
6. **配置死接线风险**：UI、持久化均成功但 `HOLD_KEYS` 未注册时，生产调度器仍使用旧配置。

## 五、生产业务场景推演

### 典型场景：无可用账号持续超过 10 分钟

timer 会唤醒请求，但按文档状态机，请求可能立即再次挂起。由于没有已证明的客户端可见正文，无法判断看守是否重置。**当前不通过。**

### 复杂场景：挂起期间修改自动放行间隔

文档要求重建 timer，但未说明旧 timer 回调已经排队时如何处理，也未定义 `nextAutoReleaseAt` 在重建瞬间的原子更新。可能出现一次额外放行或 UI 短暂展示旧时间。需在契约和 FakeClock 测试中明确。

### 极端场景：自动放行、手动放行、timeout 同时竞争

一次性 CAS 不变量方向正确，但仍需验证只有成功认领方增加计数、更新下一次时间并触发推送；失败竞争者不得产生虚假累计次数。

### 组合场景：Layer C 首字节看守启用

按文档给出的 200 秒与 480 秒默认值，请求会在下一轮自动放行前终止。当前依靠未来实现方人工核对，生产闭环不成立。

## 六、架构判决

**当前架构错误需重设计。**

准确说，需要先重新确认功能所属责任层：若 `releaseAll()` 确实不能在无号时造成客户端可见的有效正文，则 HoldGate 自动唤醒不是实现用户目标的正确边界。必须先完成锁定样本实验，再决定保留 HoldGate 方案还是移动到真正控制响应流的层。
