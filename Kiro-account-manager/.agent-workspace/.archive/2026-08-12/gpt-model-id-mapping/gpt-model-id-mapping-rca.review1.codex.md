# 第 1 轮评审结论

## 原始问题与成功判据

当前 RCA **未锁定原始问题**。

文档开头称“所有 GPT 系列模型被统一映射为 GPT-5.6”，但没有给出：

- 目标输入样本；
- 经过哪个入口；
- 修复前实际生成的 `modelId`；
- 对应上游响应；
- 用户最终看到的结果；
- 发生时间或适用版本。

“存在上游不接受与档位/计费语义错位两类偏差”是问题集合，不是单一可证伪命题。更关键的是，修复仍会把裸名、旧名及未知未来 GPT 名归一到 Sol，因此可能把原投诉行为的一部分固化为设计。

成功判据同时要求“请求成功”与“用户知道实际档位和倍率”，但目前只有服务端 `warn`，没有证明最终用户能够看到实际模型替换及计费语义。

## 首个偏离点与因果链

文档给出的主链可归纳为：

`客户端模型名 → translator → mapModelId → payload.modelId → Kiro 白名单校验 → 流式响应或 400`

其中 `kiroApi.ts:913` 可以是“未知 GPT 名被透传并导致 400”这条链的首个偏离点。

但 RCA 又同时纳入：

- 上下文窗口推断；
- `/v1/models` 静态广告；
- `modelFamily` 分组；
- DiagnosePage 测活候选。

这些不是透传正则导致的下游结果，而是各自独立的数据维护或契约同步问题。当前文档把多个首次偏离点归到一个根因之下，因果树不成立。

## 主要问题

### A1 — 原始故障命题与修复目标不一致

- **定位锚点**：`用户报:所有 GPT 系列模型被统一映射为 GPT-5.6。`
- **问题**：没有锁定至少一个原失败样本；同时修复方案仍把多类 GPT 输入统一归一到 Sol。
- **问题根因**：把“避免上游 400”直接提升为总体成功目标，没有先区分 canonical ID、受支持别名、历史兼容别名和未知模型名。
- **业务影响**：无法判断修复是在消除故障，还是用“成功返回”掩盖模型身份、能力和价格错配。
- **架构影响**：输入模型 ID 同时承担 canonical identifier 与宽松 alias 两种职责，契约边界含混。
- **修改建议**：补齐一个原始失败样本的入口、输入、修复前映射、上游结果和用户结果；分别定义 canonical、显式别名、未知 ID 的预期行为，并说明哪些归一规则来自用户决策。
- **优先级**：**P0**

### A2 — 真实端到端验证没有穿过修复点

- **定位锚点**：`**消费锚点**:最终 sink = 上游`
- **问题**：当前实测是直接向上游发送已经 canonical 化的 `gpt-5.6-sol` 和 `claude-opus-5`，只能证明目标 ID 可用，不能证明客户端输入经过 `translator → mapModelId → 上游 → 客户端响应` 后正确。
- **问题根因**：把“修复目标可被上游接受”当成了“修复后的完整链路有效”。
- **业务影响**：映射未生效、入口旁路、响应模型未披露或流式响应异常时，现有验证仍可能全部通过。
- **架构影响**：producer 与最终 sink 分别验证，但未验证两者真实装配关系。
- **修改建议**：补充三条请求级闭环证据：原失败样本、正常 canonical 对照、高风险未知或未来名边界；均应从真实代理入口发起并验证最终内容、有效模型身份和失败语义。
- **优先级**：**P0**

### A3 — 多个独立缺陷被合并成单一根因

- **定位锚点**：`次生偏离(同根因,元数据侧未跟上上游):`
- **问题**：token 窗口、静态广告、模型分组和测活候选并非透传正则的次生后果。
- **问题根因**：以“都与模型目录有关”替代逐条因果证明。
- **业务影响**：各修复项是否真正解决对应用户故障无法独立判断，也可能把无关改动混入一次修复。
- **架构影响**：文档自身表明同一模型目录事实散布于至少四个位置，仍存在多真源漂移风险。
- **修改建议**：建立主故障链与并列变体链；为每个变体分别列首次偏离点、直接证据、用户影响和验证。明确判定这是单点本地缺陷，还是模型目录缺少权威来源的架构缺陷。
- **优先级**：**P1**

### A4 — 未知模型静默降级与成功状态冲突

- **定位锚点**：`Kiro 未来新增 GPT tier`
- **问题**：未来有效的 `gpt-5.7-sol` 会被静默改成 `gpt-5.6-sol`；服务端日志不能证明用户知道发生了换档。
- **问题根因**：把可用性置于模型身份契约之上，却没有定义用户可见的降级协议。
- **业务影响**：用户可能在不知情时获得不同能力、上下文窗口或计费倍率。
- **架构影响**：未知 canonical ID 与兼容 alias 被同一 fallback 处理，削弱模型 ID 作为契约标识的可信度。
- **修改建议**：补充真实业务场景、缺失影响和业务分类；明确未知 canonical ID 是显式拒绝、受控降级并回传有效模型，还是仅允许已登记别名归一。任一策略都应与成功状态一致。
- **优先级**：**P1**

### A5 — 静态兜底清单与区域/账号实测相互矛盾

- **定位锚点**：`地区决定返回子集`
- **问题**：文档已确认不同访问路径只能获得 6 或 17 个模型，却又把 17 个模型写入全局静态兜底清单。
- **问题根因**：把一次账号、区域及代理条件下的动态可用性结果固化为全局能力事实。
- **业务影响**：动态查询失败时可能向用户广告其账号或区域实际不可调用的模型，再次产生“列表可见但请求 400”。
- **架构影响**：模型固有元数据与租户/区域运行时可用性没有分层；易变倍率也可能再次陈旧。
- **修改建议**：说明静态清单的适用范围、失效行为和新鲜度依据；区分模型元数据与账号/区域可用性。若现状无法保证，应将该点标注“需实现方核实”，不得宣称已闭环。
- **优先级**：**P1**

## 根因判决

**ARCHITECTURE_DEFECT**

主 400 故障表现为局部错误分支，但文档呈现出更上游的契约问题：

1. canonical model ID 与兼容 alias 没有清晰边界；
2. 模型目录、窗口、倍率、广告和测活候选存在多份表示；
3. 固有模型元数据与账号/区域可用性未明确分层。

`mapModelId` 的正则是主失败链的局部首个偏离点，但不是全部五处改动的共同根因。

## 修复有效性判决

**尚不能证明必然阻断原失败链。**

已有证据能证明：

- 若最终发给上游的是两个已测试 canonical ID，上游能够出流；
- 单元测试和类型检查通过。

尚不能证明：

- 原失败输入确实经过修复后的映射路径；
- OpenAI 与 Anthropic 两个真实入口都使用了新规则；
- 用户最终获得内容并获知实际模型与倍率；
- Terra/Luna 等 canonical ID 不会被误归一；
- 静态兜底不会向受限区域或账号广告不可用模型。

## 副作用与回归风险

1. 未知未来模型会被静默换成 Sol，可能造成能力与费用语义错配。
2. GPT-4 历史别名的倍率从 1.3x 升至 2.4x；虽称已有用户决策，但需核实受影响终端用户是否有可见提示。
3. 17 项静态目录可能在仅支持 6 项的环境中制造假可用模型。
4. 多文件模型元数据仍可能再次漂移。
5. 固化一次端点实测倍率后，未来价格变化可能重现本次问题。
