## 🏗️ 1. 边界决策

**成功状态(来源:用户原话「要从中找到一个舒适点」「如何减少这个 429」)**:
`NOT「429 次数变少」, BUT「白天高峰期发一次 10-40 万 token 的对话,等待时间可预期(不再出现 200-361s 长尾),且不因限流失败」`
负条件:不得为降低 429 牺牲最终成功率(当前客户端成功率实测 97-100%,是**基线不得退化**);不得把 429 误判为额度耗尽(RCA 2026-08-04)。

### 问题重新定位(修正此前方向)

429 是**外部共享容量竞争**的结果 —— 用户实测「凌晨人少几乎不限流,白天人多严重」,我方凌晨测得 26 次请求(含 82 万 token)零 429,**印证了这一点**。这意味着:

- ❌ **不可控**:上游总容量、其他用户的用量、限流窗口的具体算法
- ✅ **可控三件事**:
  1. **少制造无效负载** —— 每次 429 重试都重传全量 payload,我方自己在加深竞争
  2. **把请求导向此刻更健康的账号** —— 实测同区域账号 429 率落差 5.4% ↔ 75%
  3. **等待期不要浪费** —— 撞 429 后原地重传 vs 换号/等容量回补

**所以本卡不再追问「429 属于 RPM 还是 TPM」**(那是上游内部实现,我方无法观测也无法改变);改为**面向可控量优化**,并用「单位成功请求的上游尝试次数 + 墙钟耗时」作为唯一优化指标。

### 核心域 vs 基础设施

限流适配属**基础设施层**(`kiroApi` 出站 + `accountPool` 选号),不进核心域。

### 状态机(账号健康度)

```
HEALTHY ──429率超阈值──> DEGRADED ──持续429──> COOLING
   ^                          |                    |
   └──── EWMA 衰减恢复 ───────┴─── 冷却到期 ────────┘
```
关键约束:**必须快速恢复**。实测账号健康度会漂移(uedxuspvs 前半段 429 率 0%、后半段 80.7%),所以禁用长冷却/静态黑名单 —— 半衰期取分钟级。

### 不变量

- 任一时刻,池中至少一个账号可被选中(EWMA 降权**不得**导致全池不可用 → 必须有 floor 权重)
- 单个客户端请求的上游尝试次数有硬上限(防止 30-90 次重传)
- 429 永不标记为额度耗尽

### ADR admission

**需要:是** —— 引入「账号健康度加权选号」改变了选号契约(现有 round-robin / sticky 语义),且未来有人会问「为什么不用简单轮询」。落 `ADR-0003 账号健康度加权选号`(Proposed → 实施后 Accepted)。

## 📊 3. 观测缺口(实施前必须补齐 —— 白天测试的前提)

**这是本卡最紧急的部分**:当前日志无法支撑「白天 vs 凌晨」对比,原因实测如下:

| 缺口 | 现状 | 后果 | 修复 |
|---|---|---|---|
| 请求日志仅 100 条 | `index.ts:6426` `MAX_LOGS = 100` | 高峰期几分钟就滚没,无法看一天的曲线 | 提到 5000 + 按天分文件 |
| 请求日志无 429 字段 | 仅 `time/path/model/status/tokens/credits/responseTime` | **看不到一次请求内部撞了几次 429** | 加 `retryCount / upstream429Count / endpointsTried / accountId / queueWaitMs` |
| 详细日志 10000 条滚动 | `logger.ts:320 maxLogs = 10000` | 40 分钟就满(实测 10435 条),跨小时对比丢数据 | 429 事件独立落盘(append-only,按天) |
| 零 TTFT 打点 | 仅 TTFB(`grep TTFT` = 0 命中) | 分不清「上游慢」vs「流式输出慢」 | `parseEventStream` 首 chunk 打点 |
| 账号维度无聚合 | 有 acc 字段但无统计 | 无法回答「此刻哪个号最健康」 | 面板加 per-account 近 5min 429 率 |

**需要观测的指标(白天测试的目标读数)**:
1. `单位成功请求的上游尝试次数`(当前基线实测 **7.3**)—— 主指标
2. `429 遭遇率` per 账号 per 小时 —— 判断健康度漂移与高峰规律
3. `浪费上传 MB / 成功请求`(基线 **1.23MB**)—— 成本指标
4. `TTFT / 总耗时 P50 / P95 / P99` —— 用户体感
5. `429 → 成功的墙钟间隔分布` —— 决定该早停还是该等

## 🧪 5. 测试边界(TDD Red)

1. `高429率账号必须被降权,但池中始终至少一个可选`(不变量,防全池锁死)
2. `账号健康度快速恢复:停止 429 后 N 分钟内权重回升`(锁住漂移场景)
3. `单请求上游尝试次数不超过硬上限`(内外层预算合并,回归 30-90 次)
4. `429 事件独立日志 append-only 不被滚动窗口丢弃`
5. 边界:全池皆高 429 率(不得拒绝服务,退化为原轮询)· 单账号池(加权逻辑不得崩)· 冷启动无历史数据(默认 HEALTHY)

## 🛡️ 6. 方案排序(按「可控性 × 收益 / 风险」)

| # | 动作 | 目标可控量 | 预期 | 风险 |
|---|---|---|---|---|
| **A** ✅已做 | full jitter | 少制造竞争 | 消除并发同步 | 无(441 测试绿) |
| **B** ⭐ | 补观测(§3) | — | **白天测试的前提** | 无(纯增量) |
| **C** ⭐ | 合并内外层重试预算 + 按 payload 缩放 | 少制造无效负载 | 重传 1.23MB→~0.4MB/请求;杜绝 30-90 次 | 低(需保成功率) |
| **D** ⭐ | 账号 429 EWMA 加权选号 | 导向健康账号 | 落差 5.4%↔75% ⇒ 最大杠杆 | 中(改选号契约,需 ADR) |
| **E** | siblingReady 短路(有健康号立刻换,不原地等) | 等待期不浪费 | 减少无效重传 | 低 |
| **F** | 入站 AIMD 令牌桶 | 少制造竞争 | 源头削峰 | 中(移植需带走两个已知坑) |

**推荐顺序:B → C → D → E,F 视 D 效果再定。**
理由:B 是所有后续验证的前提(否则白天测了也读不出);C 风险最低且立即减少自造负载;D 收益最大但需 ADR 与充分测试;F 是最重型的,若 D 已把请求导向健康号,削峰的边际价值下降。

### 明确不做

- ❌ 继续论证「大 payload 是否导致 429」—— 三种口径(按 attempt / 按 request / 第三方无重试实现)均未支持,且**即使成立也不可控**
- ❌ 调 `baseMs`(实测占单次往返 2.1%,伪旋钮)
- ❌ 反推上游限流算法归类(不可观测、不可改变)
- ❌ 长冷却 / 静态账号黑名单(健康度会漂移,实测 0% → 80.7%)
