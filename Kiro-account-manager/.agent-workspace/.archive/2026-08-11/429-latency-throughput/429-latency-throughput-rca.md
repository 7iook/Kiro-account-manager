## 🔍 2. 根因分析

### 2.1 第一分歧点

`src/main/proxy/kiroApi.ts:2244-2289` —— 429 处理的策略假设与真实机制不匹配。

代码注释(2246 行)声明的模型:
>「429 = 概率式限流(窗口随机开关)。策略:短 backoff + 高重试次数,让请求密集打向服务端有更大概率命中开窗。」

**实测修正**:限流不是"随机开窗",而是**绑定在「账号×端点」组合上的容量状态**。证据:同时刻 EU 1% vs US 47%。正确动作是**换组合**,不是**原地敲门**。

### 2.2 真实成本结构 —— 本次审查最重要的数字

```
429 响应 TTFB   p50 = 1880ms(风暴窗) / 2476ms(我的窗)   ← 上游收完整个 payload 才拒
200 响应 TTFB   p50 = 3534ms / 4717ms
50ms backoff 占单次 429 往返 = 2.1%
```

**429 不是即时拒绝**,它在完整接收 0.77MB 之后才返回。因此:

- 调 backoff(0/10/50/100/250/500ms/指数/jitter)最多影响总耗时 **2.1%**,**是伪旋钮**
- 真实成本 = 每次重试**重新上传整个 10-40 万 token 上下文** ≈ 1.9-2.5s
- 实测浪费上传:风暴窗 **95MB**/29min,我的窗 **37MB**/29 请求(**1.23MB/请求**)

用户提出的「系统测试 0/10/50/100/250/500ms/指数/jitter 找最佳平衡点」这个实验**不必做** —— 自变量只能影响 2.1% 的耗时,信噪比不足;真正的自变量是「重传次数」与「端点选择」。这是本轮最该纠正的方向。

### 2.3 重试的边际收益(客户端结局锚定)

我的实验有 ground truth:29 次请求 **100% 成功**,内部吸收 60 次 429、158 次重试、恢复率 **98.3%**。

```
<= probe 1: 30.5%    <= probe 3: 84.7%
<= probe 2: 69.5%    probes 4-10 仅追加 15.3%
```

**结论有两面,必须都说**:
- ✅ 重试**确有价值** —— 把 60 次 429 全吸收,客户端零失败,不能简单砍掉
- ❌ 但**探测 4-10 只贡献 15.3%**,占用 87% 预算,且是 §2.4 拥塞来源

### 2.4 拥塞自强化(与对比项目独立印证)

hazard 随已流逝时间**单调下降**(0-0.5s:29.5% → 4-6s:4.8%)。若是"等窗口开",hazard 应随等待上升。实测反向 ⇒ 重试在推远容量。

jsjm1986 `provider.rs` 的独立实证描述同一机制:
>「小号池下重试循环反复选到同两个号,单请求就把 trigger_count 刷到 7、冷却 15→72s,**自造雪崩**」

### 2.5 Retry-After 实测缺席(双源交叉验证)

主项目 860 次 429 中 **0 次**出现 ≥1000ms wait ⇒ 上游从不给 `retry-after`。Quorinex 独立实测 **474/474 全空**。`kiroApi.ts:2257` 的 header 分支是死路径(留着无害)。

### 2.6 缺失的层

- **无入站速率整形**:`git grep` 确认无令牌桶/漏桶/自适应并发。唯一"控制"是失败后重试与冷却 —— 即 jsjm1986 批评的「冷却是号挂了之后的补救,减不了并发」
- **无 siblingReady 短路**:Quorinex 明确「有空闲号立刻换,不等待」;主项目在内层 429 循环里死等 8-10 次才让位给端点回退
- **端点选择不按 429 反馈学习**:EU 1% 就在池里,却让 US 47% 承担 125 次尝试

### 2.7 配置真值

代码默认 `baseMs=400`,实测生效 **50ms**(waits min=50/max=62/mean=53)。用户描述的"10ms"在数量级上接近实际值。

**bug 分类**:☑ 责任边界违规(把容量管理外包给盲目重试)+ ☑ 接口契约理解错误

## 📚 5. 业界参考与对比项目差异

| 机制 | 主项目 | Quorinex-go | jsjm1986 |
|---|---|---|---|
| 429 重试预算 | 8-10 次 × ~53ms ≈ **5s** | **6 分钟** | 靠入站整流少触发 |
| 退避形状 | 固定 + **±25% jitter(±12ms)** | 几何 + **full jitter**,cap 20s | — |
| 有空闲号时 | ❌ 仍死等重试 | ✅ **siblingReady → 立刻换号** | ✅ 换号 failover |
| 入站速率整形 | ❌ **无** | ❌ 无 | ✅ **令牌桶 + AIMD** |
| 按 429 自适应降速 | ❌ 无 | ❌ 无 | ✅ ×0.5 乘性减 |
| 首次 429 才罚 | ❌ 同链重复累加 | — | ✅ **同链只降一档**(去抖 3s) |
| 端点按 429 率择优 | ❌ 固定顺序 | — | ✅ EWMA 健康分 + 熔断 |

**±25% jitter 实质失效**:±12ms 抖动 vs 1.9s 请求时长,解相关能力可忽略。Quorinex 明确必须用 **full jitter**(`[0,window)` 均匀取样),否则并发调用者重新同步成 thundering herd。

- AWS Builders' Library "Timeouts, retries, and backoff with jitter"(Marc Brooker)—— retry 放大过载,须配 **retry budget**
- Google SRE Book Ch.22 "Addressing Cascading Failures" —— AIMD 为标准姿势
- GitHub `kirodotdev/Kiro#8998` —— credits 充足仍 429(佐证非配额型)

## 🛠️ 6. 手术式修复(按实测收益排序)

**P0-A · 端点按 429 率择优 + siblingReady 短路** ⭐ 收益最高
- 依据:同时刻 EU 1% vs US 47%,却让 US 跑了 125 次
- 改 `kiroApi.ts` 端点选择:维护每「账号×端点」EWMA 429 率,优先低率组合;内层 429 循环在**存在低率替代组合时立即让位**(不再死等 8 次)
- 预期:429 遭遇率 28-49% → 接近最优端点的 1-5%

**P0-B · 重试预算按 payload 缩放 + 早停**
- 依据:probes 1-3 解决 84.7%,4-10 仅 15.3%;每次重传 0.77-3MB
- 改:`maxAttempts` 固定 8 → `payload<0.5MB→4 / 0.5-1.5MB→3 / >1.5MB→1`
- 预期:浪费上传 1.23MB/请求 → ~0.4MB/请求,并减轻 §2.4 自强化

**P0-C · jitter 改 full jitter**
- 现 ±25%(±12ms)→ `[floor, window)` 均匀取样,floor=250ms
- 零风险,直接消除并发同步

**P1 · 入站 AIMD 令牌桶**(移植 jsjm1986 `throttle.rs`)
- 位置:`proxyServer.ts` 入站关口(选号前);初始 target_rpm 由实测反推(**~12 RPM 稳定态**),floor 6/ceiling 30,burst 2s
- **必须带走的两个已知坑**:target_rpm 读改写需同锁(否则降档被升档覆盖);容量 `.max(ONE_TOKEN_MILLI)`(否则低 RPM 时限速永久失效)
- 排队超时**放行**不拒绝

**P2 · 长耐受等待**(移植 Quorinex,仅在无低率端点可换时)
- 预算 60-90s(不取其 6min,主项目已有 HoldGate 负责长挂起)
- 前置:确认 429 等待期间 SSE 心跳在发(当前 HoldGate 只覆盖"无可用号",**429 场景未覆盖**)

**P3 · 补 instrumentation**(实测缺口)
- **零 TTFT 打点**(`grep TTFT|first.?token` = 0 命中),只有 TTFB
- 请求日志只留 100 条且**无 status/retry_count/retry_delay/endpoint 字段**
- 需加:TTFT、retry_count、429_count、endpoint、queue_wait_ms

### 明确不改(避免下游打补丁)

- ❌ **不做「重试窗口 0/10/50/…/500ms 对比实验」** —— 实测只占耗时 2.1%,伪旋钮(对用户原始测试方案的修正)
- ❌ 不删 Retry-After 分支(上游未来可能补)
- ❌ 不动 `accountPool` 的 429→RECOVERABLE 分类(RCA 2026-08-04 已正确)
- ❌ 不动 HoldGate 语义(职责是"无可用号",与 429 正交)
