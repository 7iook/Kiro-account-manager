**NOT** 「服务端能启动 / 测试全绿 / Docker 镜像能构建」，
**BUT** 用户把它跑在一台 Linux 服务器上之后 **关掉自己的电脑**，反代仍在对外服务、手机面板仍能管账号（看额度 / 导入 ksk_ / 选号启停 / 放行挂起）；且桌面端积累的反代行为一个不丢 —— 挂起门闸、快速重试的反直觉参数、EU/跨区端点回落、prompt cache 保真、429 与 402 的语义分离。

**来源**：用户原话「我想的是保留我们这个项目我自己的一些改动，比如说封禁一直卡的请求」+「我保留我们这个对反代的一些优化」+ 最初的「不依赖我的电脑一直开机」。

**Must NOT happen**：
1. **账号数据路径写错** → 读不到既有账号、或写到新位置导致「账号消失」。本项目最高危失效，13 处 `app.getPath` 是集中风险点。判据：迁移后既有用户在桌面端仍看到原有账号，一个不少。
2. 凭据加密降级**静默**发生（Linux 无 keyring → 备份退化明文，`secureBackup.ts:33-43` 已有降级路径但用户无从得知）。
3. 桌面端因抽取而回归 —— 两端必须共用同一内核，不得出现「服务端修了桌面端没修」。判据：现有 1180 测试全程绿。
4. 服务器上暴露面扩大而鉴权未随之评估 —— 物理机器边界这道隐性保护消失了。
5. 语义失效的功能在服务端「看起来能点」（切换本机 IDE 登录态 —— 服务器上没有 IDE）。
6. **内核层重新引入 electron 依赖而无人发现** —— 靠注释挡不住下一个人，故 K-4 用编译期强制。

### 数据目录并发：按场景分，不是一刀切（用户裁决 2026-08-10）

用户原话：「部署到服务器肯定是不需要那个桌面，但是在我们自己本地跑的话需要这个桌面。你这个得分情况。」—— 此前把两个场景混成一个问题是主 AI 的框定错误。

| 场景 | 实际情况 | 需要什么 |
|---|---|---|
| 服务器 | 只有服务端进程，独占数据目录 | **什么都不需要** —— 锁永远拿得到，等于不存在 |
| 本地 · 只开桌面端 | 现状，同今天 | 不变 |
| 本地 · 两个都开 | 唯一有风险的组合 | 第二个进程**明确报「已有实例占用此数据目录」并退出**，而非静默损坏 |

**已核实的风险来源**：`accountService/state.ts:124-179` 的锁注释自证是「**进程内**串行锁」，防的是「定时器与 IPC 在同一 tick 交错读改写」；revision 仲裁是应用层的、**且只在调用方显式传 `expectedRevision` 时启用**，而主进程侧的权威写入（如 token 刷新）刻意不传。故两个独立进程各持自己的锁、互不可见 → 后写者整体覆盖先写者。

**外部实践支持这个做法**：Electron 官方机制就是 `requestSingleInstanceLock()` + 拿不到则退出；Wails 同样（命名互斥体 / dbus）。反面教材 `eclipse-theia/theia#10890`：默认未开单实例锁 → 第二进程拿不到数据库文件锁 → **自己造了一份新的，所有应用级设置被重置**，正是此处要防的失效形态。另注 `electron/electron#33975`：连官方那把锁在跨用户会话时都出过崩溃 —— 自造跨进程互斥的风险高于采用现成机制。

**因此不做**：跨进程真互斥锁 / 桌面端降为只读。前者风险高于收益（账号数据是最不能丢的东西），后者要逐个判定「哪些算写」（token 自动刷新在定时器里也是写），改动面大且易遗漏。


### 数据真源与迁移（DC2 · 评审 P0 · 此前只定了并发锁却漏了「数据从哪来」）

评审指出的真问题：此前把三种**互斥**的数据模型混在一起 —— 共享同一份路径 / 复制迁移 / 双端并发。锁只解决「谁能写」，没解决「服务器上那份数据从哪来、谁是权威」。

**已定：服务器与本地各自持有独立数据副本，无共享、无同步。**

| 项 | 决定 | 理由 |
|---|---|---|
| 数据真源 | **各自独立** —— 服务器上那份是权威，本地那份是权威，互不同步 | 两台机器共享一份账号数据需要网络文件系统或数据库，而 `electron-store` 是本地 JSON；强行共享等于自造分布式存储 |
| 初始数据来源 | **一次性人工复制**（导出/导入，或直接拷数据文件） | 迁移是一次性动作，不是持续同步 |
| 迁移后双向变更 | **不合并** —— 服务器上导入的新账号不会回到本地，反之亦然 | 无同步机制即无冲突可能；用户需知道这一点 |
| 若用户想双向 | **本轮不做**。可用的替代是「只在一处管账号」（推荐服务器）+ 另一处只读查看 | 双向同步是独立项目，牵涉冲突解决语义 |

**因此 I1 需改写**：不是「迁移不改变数据位置」（那假设了共享），而是：

- **I1a**：服务器读取的数据格式与桌面端**完全兼容** —— 同一份 `kiro-accounts.json` 拷过去即可用，不需要转换脚本。
- **I1b**：迁移**不修改源数据** —— 复制而非移动，本地那份保持可用（回退路径）。
- **I1c**：单实例锁按数据目录生效（见上节）—— 防的是同一台机器上两个进程指同一目录，不是跨机器。

**用户可观察的判据**：把本地数据文件拷到服务器 → 启动服务端 → 面板上看到的账号数量、邮箱、额度与本地桌面端**一致**；本地桌面端此后仍能正常打开、数据未被改动。

**失败行为（必须定义，不得静默）**：

| 情况 | 行为 |
|---|---|
| 数据文件不存在 | 以空账号库启动，面板提示「未找到账号数据，请导入」—— **不是崩溃，也不是静默建空库** |
| 数据文件存在但解不开（密钥不符 / 损坏） | **拒绝启动**并明确报「数据文件无法解密」，绝不以空库启动（否则用户以为账号丢了） |
| 数据文件是更新版本格式 | 拒绝启动并报版本不符，不做向下猜测解析 |
| 数据目录无写权限 | 拒绝启动 —— 只读运行会让所有写操作静默失败 |

### 密钥与加密边界（DC3 · 评审 P0 · 三套机制此前混为一谈）

评审指出本项目实际有**三套**不同的加密/密钥，此前只写了「用同一个 encryptionKey」，把它们混了：

| # | 机制 | 现状 | 服务端处置 |
|---|---|---|---|
| 1 | **主数据加密** —— `electron-store` 的 `encryptionKey`，硬编码在源码里（`index.ts:1955-1966`） | 它是**混淆不是安全**（密钥在源码中，任何人可读） | **必须沿用同一个值**，否则读不开既有数据。**不因迁移而提升其安全性** —— 那是独立议题，且改了会让老数据读不开 |
| 2 | **备份加密** —— `safeStorage`（`secureBackup.ts:26/36/52`），依赖操作系统凭据存储 | Linux 无 keyring 时已有降级：写明文 `.backup.json`（`:33-43`，文件头注明为此场景准备） | 见下「降级三态」 |
| 3 | **面板 adminKey** —— 256bit 随机，`webPanel/auth.ts` | 与上两者无关，是访问凭据不是加密密钥 | 不变。轮换语义已实现（轮换即失效所有会话） |

**降级三态**（⚠️ **此表仅适用桌面端在 Linux 上的情形**；服务端不用 keyring，其三态见下「服务端备份加密单一真源」）：

| 情况 | 行为 | 为什么不是别的选择 |
|---|---|---|
| keyring 可用 | 备份加密，同桌面端 | — |
| keyring 不可用，**用户未表态** | **拒绝生成备份**并明确告知「此环境无法加密备份，如接受明文请显式开启」 | 静默写明文是当前行为，但服务器上凭据明文落盘的后果远重于桌面端 —— 用户必须知情 |
| keyring 不可用，**用户显式接受明文** | 写明文，并在面板上常驻可见标记 | 一次性提示会被忘记；常驻标记让「我的备份是明文」保持可见 |

**主数据加密的诚实标注**：它是混淆。服务器上文件系统权限是实际的保护层，这一点必须写进部署文档 —— 用户可能以为「加密了就安全」。若要真加密主数据，正路是自管密钥（Node crypto + 环境变量注入），属独立议题，**不在本轮**。

#### 服务端备份加密：单一真源（DC11 采纳 · 此前两处写法冲突）

⚠️ **R1 遗留的矛盾**：三态契约以「Linux keyring 是否可用」为条件，而端口表把服务端实现写成「Node crypto + 环境变量」—— **两者是不同的密钥来源与失败模型**，实现方会按不同章节做出不同东西。现统一：

| 项 | 决定 |
|---|---|
| **服务端不使用 keyring** | `safeStorage` 是 Electron API，纯 Node 下不存在。服务端**不尝试** keyring，故「keyring 是否可用」这个条件**在服务端不适用** |
| 服务端密钥来源 | **环境变量**（如 `KIRO_BACKUP_KEY`）。未设置 = 无备份加密能力 |
| 因此三态改写 | ① 环境变量已设 → 加密备份 ② **未设且用户未表态 → 拒绝生成备份并告知** ③ 未设但用户显式接受明文 → 写明文 + 面板常驻标记 |
| 桌面端不变 | 桌面端继续用 `safeStorage`；keyring 三态是**桌面端在 Linux 上**的问题，与服务端无关 |
| **加密格式必须互通** | 桌面加密的备份要能在服务端解开，反之亦然 —— 否则备份无法用于迁移。若两端格式不互通，则**服务端只支持明文备份导入**，且必须写进文档 |

#### 本轮正式支持的迁移工件（DC11 指出此前含糊）

| 工件 | 本轮支持 | 说明 |
|---|---|---|
| **原始数据文件直拷**（`kiro-accounts.json`） | ✅ **唯一正式支持路径** | 同 encryptionKey 故格式天然兼容（I1a）。这是最简单也最不易错的路径 |
| 备份文件导入（`.backup.enc` / `.backup.json`） | ⛔ **本轮不支持** | 加密备份用 `safeStorage`，服务端解不开；明文备份可行但引入第二条导入链与第二套失败模型。**不做**，直到有人真的需要 |
| 逐个重新导入 ksk_ | ✅ 已有（面板导入功能） | 账号数少时的兜底路径，无需任何迁移工具 |

### 不变量

- **I1a 格式完全兼容**：同一份 `kiro-accounts.json` 从本地拷到服务器即可用，**不需要转换脚本**。⚠️ 此前 I1 写成「两端指向同一可达路径」是错的 —— 那假设了共享存储，与「复制迁移」互斥（DC2 指出的三模型混用）。已定为各自独立副本，详见「数据真源与迁移」节。
- **I1b 迁移不改源数据**：复制而非移动，本地那份保持可用（回退路径）。
- **I1c 单实例锁按数据目录**：防同机两进程指同一目录，**不是**跨机器同步。
- **I2 内核零 electron**：由编译期强制（独立 tsconfig `"types": []` + lint `no-restricted-imports`），不靠注释。检索须覆盖 ESM / CJS `require` / 动态 import 三形态 —— 之前只查 ESM 漏掉了两个文件。
- **I3 桌面端不回归**：现有 1180 测试全程绿是度量。抽取属重构，行为不变。
- **I4 加密降级可见**：若 Linux 上 keyring 不可用导致备份退化明文，必须有用户可见的告知，不得静默。
- **I5 单一内核**：两端共用同一份内核代码，不得出现分叉的第二实现（否则「服务端修了桌面端没修」）。
- **I6 时间冲突须在合并时处置**：合并 `feat/hold-gate-auto-release` 时必须处置自动放行（480s）与 Layer C 首字节超时（200s）的冲突 —— 那是**已落地代码之间的真实冲突**（台账 #36）。⚠️ 此前写成「429 耐受与挂起门闸共用一份记账」是错的：429 耐受属范围三分的第③层、本轮不做，一个条件性能力不该占据不变量位置（DC6 指出，已采纳降级）。共账要求已移入 429 耐受任务自身的前置条件。

### ADR admission

**需要**。理由：本轮引入内核/壳分层、改依赖方向（业务层从「被 electron 装配」变为「被注入端口」）、新增六个运行时端口抽象 —— 属架构边界变更而非实现细节。ADR 应记录：为何选抽内核而非无头 Electron（官方提案已关闭 + Wayland 迁移）、为何用编译期强制而非约定、以及端口清单本身。

### 停止条件（DC7 部分采纳 · 不做纸上三方案比较，改为量化中止判据）

评审要求系统比较「沿用现状 / 局部远程化 / 抽共享内核」三方案。**驳回该形式**：沿用现状即「你电脑必须一直开」，正是待解问题；无头 Electron 的官方提案已关闭（前序已查证）；候选宿主评估已花四路侦察并已裁决。在此之后再补一轮纸上比较是形式主义。

**但评审附带要的「停止条件」有价值，采纳**。以下任一命中即**暂停并回报用户**，不得靠加尝试次数硬推：

| 触发 | 判据 | 处置 |
|---|---|---|
| 数据不兼容 | 服务端读不出既有账号，或读出数量/字段与桌面端不一致 | **立即停** —— 这是 I1a 失守，等于迁移无意义 |
| 依赖无法隔离 | 某内核文件的 electron 依赖无法用注入解开（例如需要 BrowserWindow 本体） | 停下评估：该功能是否本就该留桌面端（注册流程已是此例） |
| 桌面端回归 | 现有 1180 测试出现无法在合理改动内修复的失败 | **立即停** —— I3 是硬约束，抽取属重构，行为不该变 |
| 装配层重写超预期 | `index.ts` 的桌面专属接口无法与内核干净切分（例如接口内混杂业务逻辑） | 停下重新分包，而不是硬拆 |
| 时间冲突无解 | 自动放行与 Layer C 的时间冲突（台账 #36）在合并时找不到可接受处置 | 停下裁决：自动放行降周期 / Layer C 上调超时 / 挂起期间豁免 Layer C，三者各有代价 |

**降级路径（若停止条件命中）**：退回「桌面端继续跑，仅把反代单独抽出作服务」这个更小的范围 —— 反代是 electron 纠缠度最低的一层（27 文件仅 1 处引用），单独抽它的成本远低于全量。此路径不能满足「手机管账号」，但能满足「电脑关机后反代仍在」。


### 面板需补的必需能力（6 项 · 逐项业务分类 · DC5 采纳补完）

「必需」的判据是**无头形态下缺了用户无法完成日常工作**，不是「功能对称」。

**分类语义纠正（DC12 采纳）**：此前把 C 写成「效率改善」，与标准 A/B/C/D 语义不符。标准含义为 **A** 业务必需 · **B** 稳定性保护 · **C** 商业能力 · **D** 技术需要。本卡涉及的能力里没有商业能力项，故只用 A/B/D。

**关于「SSH 能替代」这个反驳（DC12 提出，此处部分驳回）**：评审说 C1/C2/C4 的「无替代」不成立，因为可以 SSH 改配置、SSH 查日志。**但「不用碰服务器」正是用户的原始需求**，不是我方添加的便利性 —— 用户要的是「不依赖我的电脑一直开机」，若每次改端口、删错号、查日志都要 SSH 登录服务器，那只是把「必须开着电脑」换成了「必须能 SSH 到服务器」，原始诉求未被满足。**来源**：用户 2026-08-09 选择「Linux 无界面服务」+ 2026-08-10「保留我们这个对反代的一些优化」的整体语境即「服务器上自治运行」。故 SSH 不构成替代。

**但评审有一处对**：C2 的损失我写成「选号列表被污染 + 会被轮到白赔失败请求」——后半句不准确。错误账号是否会被选中取决于池的准入与可用性判据，而那些判据已相当严格。**修正后的 C2 损失**：导入错的号无法删除，选号列表长期带着无效项，用户每次选号都要重新辨认哪个是错的 —— 是**可用性劣化**而非**每次白赔请求**。分类因此从 A 降为 **B**。

| # | 能力 | 角色 · 具体操作 | 缺失损失（具体，非「不方便」） | 现有机制能否替代 | 类 | 落点接口 | 最终消费者 |
|---|---|---|---|---|---|---|---|
| C1 | 反代低风险配置 | 运维在手机上改反代端口 / 加 API Key / 开日志 | 端口冲突时只能 SSH 改文件重启；API Key 泄漏时无法在手机上换 | ❌ 无替代（面板零配置端点） | **A** | ⛔ 待建 `POST /api/proxy/config`（白名单键） | 反代运行时 + 外部客户端连接串 |
| C2 | 账号删除 / 编辑 | 运维删掉导入错的号、改备注分组 | 导入错的号无法删除，选号列表长期带着无效项，每次选号都要重新辨认哪个是错的（**可用性劣化**；此前写成「会被轮到白赔请求」不准确 —— 池的准入与可用性判据已相当严格） | ❌ 无替代（面板仅 list + import） | **B** | ⛔ 待建 → `applyAccountDataMutation` | 账号池选号 + 面板列表 |

| C4 | 日志查看 | 运维排查「为什么请求失败了」 | **具体损失**：反代返回错误时，判据全在日志里（挂起原因 / 端点回落 / 429 与 402 分流）。无桌面时**唯一**获取途径是 SSH `tail`——而这正是「不用碰服务器」要消除的 | ❌ 无替代 | **A** | ⛔ 待建（须经 `respond.ts` 脱敏出口） | 运维人眼；**非**告警系统（告警是独立项，见运营注册） |
| C5 | 自动换号调度 | 运维开启「余额低于阈值就提前换号」 | **当前状态：该开关在反代侧从未生效**（额度今晚才刚接进池，且阈值判定在渲染进程）。服务器上渲染进程不存在 → 整块静默失能 | ❌ 无替代 | **A**，但**依赖台账 #10 换号收口** | 收口后才有落点 | 反代选号 |

**若强行在本轮做 C5 会怎样（这是它必须排除的实质理由）**：面板上会出现一个「自动换号已开启」的开关，而它反映的标志位只被一个在服务器形态下**不存在**的进程读取 —— 开关位置与系统实际行为无关。这不是「功能不完整」，是**一个看起来诚实的谎**，比没有这个开关更糟。

**已核实的两条边界（供后续实施时先写红）**：
- 阈值单位是 **credits**（界面标签「余额阈值」，`SettingsPage.tsx:906-917`），非 token。阈值经 `parseInt` 取整而 `remaining` 因 `*WithPrecision` 可为小数。
- `limit === 0` 的未刷新账号是**双向陷阱**：同一判据既判它「已耗尽需切换」又把它排除在候选外 → 满池未刷新时静默不切。这是新决策函数最该先写红的边界。

**主进程侧已有的落点（不是从零造）**：`proxy/activation.ts:205 activateProxyAccount` 已含三步编排（入池 → 写 selectedAccountIds → 移指针+失效粘性）、带依赖注入接口与 2026-07-28 RCA 的完整 why 注释，且已被局域网面板使用。新决策函数产出 accountId 后调它即可，**不得另起顺序真源** —— 该文件头部明确警告过这一点。

**处置结论**：C5 移出本轮，转台账 #10（换号决策收口）。**该项落地时必须与「停掉渲染进程定时器」同轮** —— 双定时器窗口内两边各自决策，而现有去重只覆盖 token 刷新、不覆盖换号编排，会出现两次换号打向不同账号。C5 的面板开关在 #10 完成后才有意义。

**注意 C4 的消费者边界**：日志查看的消费者是**人眼**，不是告警系统。把两者混为一谈会导致「以为有了日志页就有了监控」——告警是运营注册里的独立项。

### ⚠️ 跨模块时间约束（已知会咬人 · 台账 #36）

|---|---|
| 自动放行降到 <150s | 每小时上游请求从 7.5 次涨到 24 次，受限账号上加深限流 |

### 公网暴露边界：TLS 与首次密钥引导（DC9 · R2 唯一 P0）

⚠️ **R1 处置的实际缺陷**：更新日志称「TLS 边界与密钥引导已并入运营注册」，但运营注册表里**只有「路由须走唯一 `guard()` 入口」**，没有 TLS 终止位置、也没有首次密钥从哪来。**声称已做而实际没做，比漏做更糟** —— 后者会被发现，前者会被信任。

#### TLS 终止位置

| 决定 | 内容 |
|---|---|
| **服务内不做 TLS 终止** | 面板与反代都只监听 HTTP；TLS 由前置可信反代（Caddy / nginx / Traefik）终止 |
| 为什么 | 服务内做 TLS 意味着自管证书生命周期（申请 / 续期 / 重载），而前置反代是这件事的成熟解；本项目已有自签证书代码（`proxyServer.ts:648` 附近取 userData 存证书）但那是给 MITM 用的，不是给面板对外服务用的 |
| **默认监听** | `127.0.0.1` —— 与现有 `isBindingExternal` 判据一致。改成外部地址需显式配置，且触发现有红线（无密钥则拒绝启动） |
| 转发头信任 | **默认不信任** `X-Forwarded-For` / `X-Forwarded-Proto`。仅当显式配置了「前置反代模式」时才信任，且需配可信来源 IP —— 否则攻击者可伪造来源 IP 绕过 IP 门禁与登录限流 |
| 负向验收 | ① 未配前置反代却直接暴露到公网 → 启动时**警告但不阻止**（用户可能在内网）② 配了前置反代模式但未限定可信来源 → **拒绝启动**（这是可被伪造的配置，比明文更危险） |

**诚实标注**：本项目**不提供** HTTPS 开箱能力。部署文档必须写明「面板经公网访问时必须前置 TLS」，而不是让用户以为「有 adminKey 就安全了」—— adminKey 在明文 HTTP 上传输等于公开。

#### 首次 adminKey 引导

现有实现（已核实）：`generateAdminKey()` 生成 256bit 随机值、`keyStore` 持久化、未配置时**拒绝放行**（注释「空 key 等于无鉴权」）、`rotateAdminKey()` 轮换即失效全部会话。缺的是**服务器上「第一次从哪看到它」**。

| 环节 | 决定 |
|---|---|
| 生成时机 | 首次启动时若无密钥 → **生成并打印到标准输出一次**（部署时用户在终端/容器日志里能看到） |
| 一次性展示 | 仅首次生成时打印；之后启动不再打印 —— 否则容器日志里长期留着有效凭据 |
| 持久化权限 | 密钥文件权限 `0600`（仅属主可读）。**若无法设置该权限则拒绝启动** —— 世界可读的凭据文件等于没有凭据 |
| 支持预置 | 允许通过环境变量预置密钥（适配 Docker secrets / 编排工具），此时不生成也不打印 |
| 遗失恢复 | 停止服务 → 删除密钥文件 → 重启（重新生成并打印）。**不提供「重置密钥」的 HTTP 端点** —— 那会是无需鉴权就能重置鉴权的自指漏洞 |
| 轮换入口 | 面板内（C6，走已实现的 `rotateAdminKey()`）；轮换后**所有会话失效含发起者**，需用新密钥重新登录 |
| 负向验收 | ① 密钥文件权限过宽 → 拒绝启动 ② 环境变量与文件同时存在且不一致 → **拒绝启动并说明**，不猜哪个优先 ③ 首次生成的密钥未出现在输出里 → 部署即失败（用户无法登录），需专门测试 |


### 运营注册（DC8 采纳 · 此前只覆盖构建产物，漏了「文件存在后如何成为可运营服务」）

| 项 | 要求 | 缺了会怎样 |
|---|---|---|
| 进程托管 | systemd unit 或 Docker `restart: unless-stopped` | **服务器重启后服务不恢复** —— 而「电脑关机也能用」正是本项目目的，托管缺失等于目的落空 |
| 启动失败反馈 | 拒绝启动的四种情况（目录不可写 / 解不开 / 版本不符 / 外部绑定无密钥）都要有可读退出信息 | 用户只看到进程退出，不知为何 |
| **TLS 与密钥引导** | 见上节（DC9） | adminKey 明文传输 / 首次部署无法登录 |
| 面板路由与鉴权注册 | 每个新增端点都在 `guard()` 之后（现有 `server.ts:346` 是唯一入口，新路由必须走它） | 漏一个 = 未鉴权端点裸奔 |
| 配置校验 | 启动时校验配置，非法值拒绝启动而非取默认值静默跑 | 配错了却「看起来在跑」 |
| 明文降级告警 | 面板常驻标记（见密钥边界节） | 凭据明文落盘而用户不知 |
| 升级 / 回滚 | 数据格式若变更需给回滚路径；本轮既定「格式不变」故仅需版本标记 | 升级失败无退路 |
| 数据备份 | 部署文档写明备份哪个文件、如何恢复 | 唯一副本损坏即全部账号丢失 |

#### 三类状态信号必须分开（DC14 采纳 · 此前把三者混成一个「健康探针」）

评审指出的真问题：我把「存活」「就绪」「业务指标」写成了一个端点，且暗示它自动构成监控与自愈闭环 —— 而**探针只是产出，没有消费者就什么都不会发生**。

| 信号 | 语义 | 真实消费者 | 消费后动作 |
|---|---|---|---|
| **存活**（liveness） | 进程还在响应 | 进程托管（systemd `Restart=` / Docker `restart:`） | **自动重启** —— 这是唯一真正自动的一环 |
| **就绪**（readiness） | 反代已绑定端口、数据已加载 | 前置反代 / 编排工具（决定是否转发流量） | 未就绪则不转发。**若无前置反代与编排，此信号没有消费者** —— 那就诚实地不做，别做一个没人读的端点 |
| **业务指标**（池有几个可用号 / 有无挂起 / 是否明文降级） | 运维判断依据 | **人**（面板上看），**不是**自动化 | 人做决定。⛔ **本轮不做自动告警** —— 告警需要通知通道（邮件 / webhook / 推送），那是独立项目 |

**因此本轮的诚实范围**：存活探针 + 进程托管（真闭环）· 就绪探针仅当部署形态里有消费者时才做 · 业务指标经面板给人看。**不声称「有监控」** —— 有监控意味着无人值守时也有人被叫醒，本轮做不到这一点。
