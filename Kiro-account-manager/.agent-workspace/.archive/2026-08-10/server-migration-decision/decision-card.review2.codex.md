# 第 2 轮评审结论

## 一、原始用户目标与可观察成功状态

- **角色**：项目管理员、Linux 服务器运维者。
- **真实操作**：迁移既有账号数据，在服务器启动服务，通过手机面板管理账号，并由外部客户端持续调用反代。
- **预期结果**：关闭桌面电脑后，服务器仍独立提供反代；手机仍能查看额度、导入账号、选号启停、放行挂起请求。
- **负向条件**：账号不得消失或被静默清空；不得静默产生明文备份；桌面端行为不得回归；无语义的桌面能力不得伪装成可用；共享内核不得重新依赖 Electron。
- **来源判断**：引用了用户原话，来源成立。

总体成功状态已经清楚，但 TLS/首次密钥引导、成功状态中部分面板操作的生产链，以及新增面板能力的业务必要性仍未闭合。

## 三、P0/P1 评审意见

### DC9【P0｜架构级/安全】TLS 与首次密钥引导被声称已纳入运营注册，实际没有契约

- **定位锚点**：`### 运营注册（DC8 采纳`
- **问题**：更新日志称“TLS 边界与密钥引导已并入运营注册”，但运营注册表没有 TLS 终止位置、反向代理信任边界、首次 adminKey 生成/展示/持久化规则。运行链只约束“外部绑定且无密钥拒绝启动”。
- **问题根因**：把“必须配置密钥”误当成完整的公网访问安全边界。
- **业务影响**：adminKey、账号信息、日志和控制请求可能经明文链路传输；首次部署可能因不知道密钥从哪里来而无法登录，或采用不安全的固定密钥。
- **架构影响**：部署边界和认证边界没有统一成立，生产接线仍不可验收。
- **修改建议**：明确默认监听范围、TLS 在服务内还是可信反代终止、转发头信任规则、首次密钥的生成与一次性展示、持久化权限、遗失恢复和轮换入口；加入负向验收。
- **优先级**：P0。

### DC10【P1｜功能闭环】成功状态、运行链、任务和 E2E 覆盖的面板操作集合不一致

- **定位锚点**：`### 最终 sink 与必须真跑的 e2e`
- **问题**：成功状态要求“选号启停”，E3也包含这些操作，但运行链没有对应 producer、consumer、状态变化和失败行为。相反，本轮新增的 C1～C4、C6 已进入 K-9，却没有进入最终 E2E。
- **问题根因**：链路按新增端点编写，E2E 按用户原始目标编写，两者没有通过同一验收矩阵收口。
- **业务影响**：可能出现用户目标中的操作未接线，或新增端点存在但生产页面从未触发。
- **架构影响**：无法证明每个面板入口均有可达 producer 和真实 consumer。
- **修改建议**：统一成功状态、任务、运行链和 E2E 的操作清单；为选号、启停及本轮确定的每项新增能力补完整链路和至少一次真实页面验收。
- **优先级**：P1。

### DC11【P1｜架构级/安全】服务端备份加密实现与三态契约互相冲突

- **定位锚点**：`### 密钥与加密边界（DC3`
- **问题**：三态契约以“Linux keyring 是否可用”为决策条件；运行时端口表却把服务端实现写为“Node crypto + 环境变量”。两者是不同密钥来源和失败模型。此外，初始迁移同时允许“导出/导入或直接拷文件”，但只定义了原始数据文件兼容，没有定义备份导入链。
- **问题根因**：资产类型虽已拆分，但服务端选定的具体适配器和唯一受支持迁移工件仍未确定。
- **业务影响**：实现方可能按照不同章节实现不同方案；备份可能无法恢复，或测试错误地接受未经显式同意的明文降级。
- **架构影响**：加密适配器、配置契约、迁移入口和测试预期没有单一真源。
- **修改建议**：选定服务端备份加密方案并统一端口表、三态、配置和测试；明确本轮正式支持原始数据复制、备份导入或二者，以及各自密钥和失败行为。
- **优先级**：P1。

### DC12【P1｜业务边界】面板能力仍存在 Solution-Jumping，且分类定义偏离固定 A/B/C/D 语义

- **定位锚点**：`### 面板需补的必需能力（6 项`
- **问题**：本卡把 C 定义成“效率改善”，而固定分类中的 C 是商业能力。C1、C2、C4 的“无替代”也不完全成立：文档自己列出了 SSH 改配置、SSH 查看日志；成功状态已有“启停”，可能覆盖错误账号继续参与选号的问题。是否仍必须新增接口，需要按真实损失重新判定。
- **问题根因**：把“不用 SSH”和“页面能力缺失”直接提升为 A 类业务刚需，未区分用户目标、稳定性保护和便利性。
- **业务影响**：迁移主链可能被非阻塞功能拖延，扩大接口和安全面。
- **架构影响**：K-9 成为未经充分裁决的横向扩面，新增第二操作入口的必要性不明。
- **修改建议**：恢复标准 A/B/C/D 分类；逐项核对现有启停、配置文件和 SSH 运维是否已覆盖业务损失。仅“无需碰服务器”若确属用户原始目标，应补来源；否则降为后续效率能力。
- **优先级**：P1。

### DC13【P1｜架构级】范围冻结后仍残留相互冲突的任务和时间契约

- **定位锚点**：`- [ ] K-7 语义失效功能的处置落地`
- **问题**：任务清单保留 K-7，注册清单也要求语义失效功能不可达；更新日志却称“K-7 不在本轮”。运行链第11跳仍写“与429耐受时间预算需共账（I6）”，而当前 I6 已明确只处理自动放行与 Layer C 冲突，429共账属于后续。
- **问题根因**：范围调整只修改了部分章节，没有对任务、链路、不变量、注册和日志做一致性回扫。
- **业务影响**：实现方无法判断 K-7 是否是交付条件，也可能误把后续429策略带回本轮。
- **架构影响**：依赖顺序和完成定义继续漂移。
- **修改建议**：裁决 K-7 本轮归属并统一所有引用；删除运行链中已经失效的 I6/429 共账表述，仅保留当前时间冲突。
- **优先级**：P1。

### DC14【P1｜部署架构】健康探针没有真实告警消费者，并错误暗示能自动重启

- **定位锚点**：`| 健康探针 | HTTP 端点报`
- **问题**：链路把“健康探针 → systemd/Docker restart → 崩溃后自动重启”写成一条因果链，但文档没有定义谁轮询、谁告警、谁基于 unhealthy 状态执行恢复。探针还混合了进程存活与“池有几个可用号”两类语义。
- **问题根因**：把状态产出当成了已经存在的监控和恢复消费链。
- **业务影响**：服务或账号池失效时仍可能无人知晓；若把业务容量直接作为存活条件，还可能产生无效重启。
- **架构影响**：可观测性存在孤儿产出，liveness、readiness和业务告警职责混淆。
- **修改建议**：拆分存活、就绪和账号池业务指标；明确探针消费者、告警接收者及恢复动作。无法提供告警系统时，应诚实限定为部署平台可查询状态，不声称“没人不知道”已解决。
- **优先级**：P1。

### DC15【P1｜决策完整性】替代方案只被口头排除，缺少成本、风险和可逆性比较

- **定位锚点**：`### 停止条件（DC7 部分采纳`
- **问题**：停止条件和降级路径有价值，但仍未比较“沿用现状”“只抽反代/局部远程化”“完整共享内核”在目标覆盖、改动规模、风险和可逆性上的差异。
- **问题根因**：把此前做过候选调查视为可以省略本卡中的决策依据。
- **业务影响**：若手机账号管理不是首期硬目标，当前方案可能承担不必要的大范围迁移成本。
- **架构影响**：ADR 缺少能解释为什么不选更小边界的自包含依据。
- **修改建议**：无需重做调查，只需把已有材料压缩成三方案对照，并说明为何用户目标必须选择路径A、何时退回“只抽反代”。
- **优先级**：P1。

## 四、断链、孤儿产出与错误消费者清单

1. TLS、首次 adminKey 引导没有生产消费者和验收动作。
2. 选号、启停出现在成功状态和 E2E，但没有运行链。
3. C1～C4、C6进入实现任务，却未进入最终 E2E。
4. 备份加密同时指向 keyring 与环境变量密钥，消费者契约冲突。
5. “导出/导入”没有对应格式、导入 consumer 和失败行为。
6. 健康探针没有明确轮询与告警消费者。
7. K-7在任务、注册和更新日志中的范围互相矛盾。
8. 运行链仍引用已经被修改的旧 I6/429 共账要求。

## 五、生产业务场景推演

### 典型场景：首次公网部署

服务可因配置了 adminKey 而启动，但文档没有说明密钥如何安全产生、首次交付给管理员，以及 TLS 在哪里终止。当前无法证明首次登录链安全可用。

### 复杂场景：迁移后完全通过手机运营

账号导入和放行已有链路，但选号、启停没有链路；新增配置、代理池、日志和密钥轮换又未进入 E2E。因此“无需桌面/SSH”的完整业务体验尚未被验证。

### 极端场景：无 keyring、需要恢复备份

文档可能分别导向拒绝备份、环境变量加密或显式明文三种实现；备份导入契约也缺失。无法判断灾难恢复是否真实可用。

### 故障场景：进程存活但账号池为空

若健康探针把池空视为不健康，托管系统可能反复重启却无法恢复账号；若只报告状态又没有告警消费者，管理员仍不会获知故障。

- 统一 K-7 与 I6 在任务、范围、链路和更新日志中的表述。
- 拆分 liveness、readiness和账号池告警，指定真实消费者。
- 在 ADR 中补三种边界方案的简要权衡。
