# 第 1 轮评审结论

## 一、原始用户目标与可观察成功状态

### 文档呈现的原始目标

- **角色**：项目管理员/服务器维护者。
- **真实操作**：把现有项目部署到 Linux 服务器，导入既有账号，通过手机面板管理账号，并让外部客户端持续使用反代。
- **预期业务结果**：管理员关闭自己的电脑后，服务器上的反代、账号池和管理面板仍可独立工作；现有反代优化不丢失。
- **负向条件**：不得丢账号、静默明文降级、引入桌面端回归、把无意义的桌面功能暴露在服务器面板中，或重新让内核依赖 Electron。
- **来源**：文档引用了用户 2026-08-09/08-10 原话，来源基本合格。

### 评审判断

成功状态本身清晰，但“服务器独立运行”与后文 **I1 两端指向同一可达路径**、E2“复制数据到服务器”存在冲突。当前还不能形成唯一、可验收的数据迁移结果。

## 三、P0/P1 评审意见

### DC1【P0｜架构级】核心接口契约和 Goal→Outcome 消费链尚未形成

- **定位锚点**：`## 📐 3. 接口契约（⛔ 核心待写）`
- **问题**：该节只有端口清单和功能盘点，没有输入、输出、稳定错误、状态变化、producer、consumer、失败行为。K-5“面板 + 反代 + 池调度”也只是组件集合，不是可验证的生产调用链。
- **问题根因**：决策仍停留在“要抽哪些模块/端口”的实现视角，没有把用户动作映射到最终结果。
- **业务影响**：可能出现服务能启动，但账号导入、放行挂起、配置修改或反代请求中至少一条生产路径无人消费。
- **架构影响**：无法验证端口是否必要、事件推送是否有真实消费者、服务端壳是否完成生产装配。
- **修改建议**：开工前补全主要链路的 producer、artifact、consumer、状态结果和失败行为；至少覆盖启动、迁移、账号管理、反代、挂起放行、配置修改和可见告警。
- **优先级**：P0。

### DC2【P0｜架构级】数据迁移、数据位置与多进程真源相互矛盾

- **定位锚点**：`- **I1 数据位置不变**`
- **问题**：I1 要求“两端指向同一可达路径”，E2 却要求把桌面数据复制到服务器；测试又把“桌面与服务端同时指向同一数据目录”留作待裁决。三者分别对应共享存储、复制迁移、并发共享三种不同模型。
- **问题根因**：未先决定账号数据的权威真源、迁移边界以及迁移后桌面端与服务器的关系。
- **业务影响**：可能导致账号消失、双端写覆盖、旧数据继续被修改而服务器读取陈旧副本。
- **架构影响**：持久化端口、锁策略、迁移测试和回滚方案都无法稳定设计。
- **修改建议**：先明确三选一模型：一次性复制后服务器独占、共享存储、或双端同步；说明迁移前后真源、并发写是否允许、冲突处理、失败回滚以及“不丢账号”的精确判据。
- **优先级**：P0。

### DC3【P0｜架构级/安全】持久化加密与备份降级契约混杂且不可验收

- **定位锚点**：`| 凭据加密 | \`safeStorage\` | 自管密钥（Node crypto + 环境变量）`
- **问题**：文档同时出现 `safeStorage`、`electron-store` encryptionKey、Node 环境变量密钥、Linux keyring 不可用及备份明文降级，但没有说明它们保护的是同一份数据还是不同工件，也没有定义旧密文如何被服务器读取。
- **问题根因**：没有拆分账号持久化、备份文件和运行时密钥三类资产的格式及密钥生命周期。
- **业务影响**：既有账号可能无法解密，或者服务器在管理员误以为仍加密时生成明文凭据。
- **架构影响**：所谓“保持同一 encryptionKey”无法证明足以保证格式兼容；密钥轮换、丢失恢复和迁移回滚均悬空。
- **修改建议**：分别明确每类资产的格式、密钥来源、启动缺钥行为、旧数据兼容、轮换方式和明文降级是否允许。若允许降级，必须指定真实通知消费者和阻止静默继续运行的规则。
- **优先级**：P0。

### DC4【P0｜架构级/安全】公网暴露与单 adminKey 的安全边界未落成契约

- **定位锚点**：`4. 服务器上暴露面扩大而鉴权未随之评估`
- **问题**：文档知道暴露面扩大，却只把鉴权保留为待评估；C6 又计划开放 adminKey 修改。未说明监听地址、TLS 边界、哪些路由受保护、初始密钥引导、轮换原子性及旧密钥失效时点。
- **问题根因**：把“单一 adminKey”当作完整安全方案，而它只是产品授权模型选择。
- **业务影响**：可能造成账号凭据、日志、配置和代理控制权被未授权访问；错误轮换还可能把管理员永久锁在系统外。
- **架构影响**：权限不变量没有统一入口，新增路由可能绕过鉴权。
- **修改建议**：定义统一鉴权中间件及覆盖范围、默认监听/TLS信任边界、密钥启动与轮换状态迁移、稳定错误和负例验收；禁止由各路由自行判断。
- **优先级**：P0。

### DC5【P1｜功能/范围】六项面板能力未逐项完成业务现实分类和任务闭环

- **定位锚点**：`### 面板需补的必需能力（6 项 · 来源`
- **问题**：C1/C2/C6给出了较明确的操作损失；C3只说“运行时依赖、刚需”，C4只说“唯一窗口”，C5仍依赖未决的换号收口。六项均未按 A/B/C/D 分类，也没有对应明确任务、接口及最终消费者。
- **问题根因**：从页面缺少端点直接跳到了“必需能力”，业务验证深度不一致。
- **业务影响**：可能漏做真正阻塞服务器运维的能力，也可能把代理池管理、日志查看做成技术上存在但用户流程不可达的页面。
- **架构影响**：K-5成为过大的兜底任务，无法判断范围是否完成。
- **修改建议**：逐项补角色、具体操作、缺失损失、现有机制、A/B/C/D分类，并映射到任务、接口、权限和验收链；答不出真实场景的删除或降级。
- **优先级**：P1。

### DC6【P1｜架构级】方案范围尚未冻结，待评估项却已进入不变量和任务体系

- **定位锚点**：`### 取经采纳项（来源 \`adopt-from-candidates.md\`）`
- **问题**：K-8仍待填，冷却分层和额度筛选待评估，I6又以“两者都上线”为条件；K-7、28处直写、双进程共享也未裁决。
- **问题根因**：必要迁移范围与可选优化没有分层，研究结果直接混入开工决策。
- **业务影响**：迁移可能被429策略等非必要优化拖延，或实现方自行选择未批准行为。
- **架构影响**：依赖图、测试范围和完成定义会持续漂移。
- **修改建议**：把范围拆成“服务器迁移必需”“保持既有行为”“独立后续优化”，所有待评估项在开工前决定纳入、延后或删除；不得让条件性能力占据当前不变量。
- **优先级**：P1。

### DC7【P1｜架构级】替代方案比较不足以支撑路径 A 的边界决定

- **定位锚点**：`### ADR admission`
- **问题**：文档论证了“不做无头 Electron”和“不整体重写”，但没有系统比较沿用现状、局部远程化、抽共享内核三条方案的收益、成本、风险、可逆性和停止条件。
- **问题根因**：外部案例和技术可行性替代了本项目的方案权衡。
- **业务影响**：若共享内核抽取成本超过迁移收益，缺少暂停或降级到更小方案的触发条件。
- **架构影响**：ADR虽被要求，却没有足够决策材料。
- **修改建议**：补三类方案比较及量化停止条件，例如无法保持数据兼容、核心依赖无法隔离、桌面回归超过阈值时应暂停还是换路径。
- **优先级**：P1。

### DC8【P1｜部署闭环】注册清单未覆盖生产运行、监控和回滚消费者

- **定位锚点**：`## 🛡️ 5. 注册检查清单`
- **问题**：已有端口注入、资产路径、依赖和文档检查，但缺少服务进程注册、启动失败反馈、健康检查、监控告警、升级回滚、配置校验及面板路由/鉴权注册。
- **问题根因**：注册检查偏向构建产物，未覆盖“文件存在后如何成为可运营服务”。
- **业务影响**：服务器重启后服务可能不恢复；明文降级、代理失效或磁盘写失败可能无人发现。
- **架构影响**：日志和告警产出缺少明确消费者，部署结果无法形成闭环。
- **修改建议**：补齐进程托管、健康探针、路由与鉴权注册、配置校验、监控告警、升级/回滚和数据备份恢复的责任方与验收动作。
- **优先级**：P1。

## 四、断链、孤儿产出与错误消费者清单

1. **事件推送端口**：服务端实现写成“HTTP / SSE / 无操作”；“无操作”会制造孤儿事件，必须按事件类型明确真实消费者。
2. **挂起放行**：面板操作存在，但待放行请求标识、状态机、过期及重复消费规则缺失。
3. **日志查看**：日志生产者存在，查询端点、脱敏、保留策略和告警消费者未定义。
4. **加密降级通知**：声明必须用户可见，但通知落到启动失败、面板横幅、日志还是告警均未决定。
5. **配置编辑**：面板是producer，但配置真源、热生效消费者和需重启状态未定义。
6. **账号复制迁移**：迁移文件有producer，但兼容读取、迁移提交点及失败回滚consumer缺失。
7. **版本/isPackaged端口**：技术用途存在，但调用点尚未清点，需实现方核实是否每个端口都有真实生产消费者。
8. **K-8采纳项**：任务占位但产出物尚不存在，当前属于不可验收任务。

## 五、生产业务场景推演

### 典型场景：管理员迁移后关闭电脑

当前可走到“复制数据并启动服务”，但密钥兼容、数据真源和启动失败行为未定义。无法证明服务器能够读出全部旧账号。

### 复杂场景：手机修改配置，同时外部请求正在挂起

配置热生效边界、挂起请求状态、重复放行和统一时间预算均未形成契约。可能出现面板显示成功但运行时未采用新配置。

### 极端场景：服务器无 keyring、环境变量密钥缺失、磁盘只读

文档只要求“降级可见”，却未决定拒绝启动、只读运行还是生成明文。该场景可能直接破坏凭据保密性或数据完整性。

### 并发场景：桌面端与服务端同时使用同一账号数据

这是文档明确未裁决的生产边界。若允许，需要跨进程锁/事务或单写者规则；若不允许，应在产品和部署层阻止，而不能只靠文档提醒。

## 六、架构判决

**调整边界。**

“共享内核 + Electron/Node薄壳”的总体方向具有合理性，但数据真源、密钥边界、鉴权边界和生产消费链尚未成立。当前不是整体架构必然错误，而是关键边界未决，不能进入实现。

## 七、开工前必核与注册清单

- 决定服务器迁移后的账号数据唯一真源及双端并发策略。
- 核实旧持久化格式、备份格式和 encryptionKey 是否确实兼容。
- 定义密钥缺失、解密失败、明文降级的稳定行为。
- 定义所有面板路由的统一鉴权、监听及TLS边界。
- 给六项面板能力逐项建立业务分类和任务映射。
- 补完启动、迁移、反代、挂起、配置、告警的消费链。
- 冻结K-8、429优化、28处直写和K-7的本轮范围。
- 注册服务进程、健康检查、路由、权限、配置、监控、告警及回滚。
- 为SSE/HTTP事件逐类指定真实消费者，禁止用“无操作”笼统实现。
- ADR在上述边界确定后再转为可执行状态。
