## 2.5 主 AI 自跑发现（不经 SUB，实测锚点）

### F-1 · `holdConfig.ts` 的「Layer C 尚未落地」注释已过期，#36 从「设计约定」变成「潜伏冲突」

`src/main/proxy/holdConfig.ts:48` 写着「2026-08-09 实测:Layer C 尚未落地(git grep + 文件系统级检索双向零结果),故这是设计约定而非在飞冲突」。
**该前提现在不成立** —— `src/main/proxy/streamWatchdog.ts:83` 的 `STREAM_FIRST_CHUNK_TIMEOUT_MS = envMs('KIRO_STREAM_FIRST_CHUNK_TIMEOUT_MS', 200_000)` 已在 `main` 上（codegraph 实读源码确认）。

后果两条：

1. **`:100-111` 的「只 warn 不强制下调」理由失效**。那段注释的论据是「Layer C 未落地时下调反而无谓缩短周期」；Layer C 既已落地，这句话本身成了下调的**支持**论据而不是反对论据。
2. **告警现在无条件刷屏**。默认配置（`autoReleaseIntervalMs=480000` ≥ `200000 × 0.75 = 150000`）必然命中，每次 `normalizeHoldConfig` 都打一条 WARN —— 实测在单个测试文件里就重复出现 6 次。

缓解事实：Layer C 挂在 `enableProxyContextSafetyNet` 开关下，**默认 false**（`src/main/proxy/types.ts:601-606`）。故 #36 目前**潜伏**而非在咬人 —— 用户一旦打开安全网就立刻生效：放行的请求会在 200s 被 Layer C 掐死，而下一次自动放行要等到 480s，用户看到的正是「自动放行开着但请求还是失败」。

→ 需要裁决的是三选一（HANDOVER §3 已列代价）：自动放行降到 <150s / Layer C 超时上调到 >640s / 挂起期间豁免 Layer C。

### F-2 · 全套件不是干净的 1679/0，有一条并行下的不稳定用例

实现方 findings 自报「1679 passed / 0 failed」。主 AI 自跑（`--reporter=json --outputFile`，读 JSON 字段而非退出码）得到：

```

numTotalTestSuites 512 · numFailedTestSuites 2 · success false
```

失败项：`test/main/proxy/proxyServerDataPathInjection.test.ts` → `ProxyServer: userDataPath 注入契约 > electron 缺席时 proxyServer 模块仍可加载`。

**单独跑该文件 14/14 全过**（EXIT=0，首条用例耗时 953ms）⇒ 不是产品缺陷。

**第二次全量复跑（run2）确认了更糟的形态**：同样 1 条失败，但**换了一个文件**：

```

      → POST /panel/api/accounts · 手机端导入 ksk_ GET /api/accounts 仍是列表（未被新路由抢走）
```

两次跑、两条不同的失败，共同点是**都要真正 bind 端口 / 生成 TLS 证书**。⇒ 结论是**并行负载下的系统性抖动**，不是任何单条用例的问题。

这条比它看起来严重，因为本项目的整套验证纪律建立在「全套件绿」之上：

- 每次全量跑都有约 1 条会红，且每次红的不是同一条。那么历史上每一句「1679/0 全绿」要么是运气，要么是**有人重跑到绿为止**。
- 一个真实回归若恰好落在这类端口绑定用例上，与抖动**在输出里完全同形** —— 正是本仓反复吃亏的那种「零结果与不存在不可区分」。

→ 这是下一阶段应当优先处理的一项：给这批要真 bind 端口的用例做隔离（串行池 / 端口分配 / 提高超时），让「全绿」重新成为可依赖的信号。**在此之前，任何「全套件绿」的声明都必须附带跑了几次、红过哪几条。**

### 侦察 E · Layer C 豁免方案（T-12 回）

**结论：取候选 (b) —— 只豁免首 chunk 超时，首个 chunk 到达后 360s inter-chunk 保护照常恢复。** 不是我原本设想的「整条豁免」。

理由站得住：HoldGate 保护的是「尚未向客户端提交语义正文」那段等待，用 200s TTFT 预算终结它与用户已选的 hold 契约冲突；但整条跳过（候选 a）会连**已经开始出字后的死流**也放过，放弃太多保护。

**它纠正了我一处判断**：我担心「给 released 请求更长但有限的首 chunk 预算」会被下一次自动放行抢先。实际不会 —— 条目在 `holdGate.ts:580-588` 的 `claim()` 时就已从 held 集合删除，请求执行上游调用期间**不存在**一个还能在 480s 再次放行同一条目的 timer。所以候选 (c) 被否掉的真实理由不是竞态，而是它只把同一问题推迟、还引入「多长才算豁免」的第二套配置关系。

**豁免范围**：请求第一次被放行后的**整个剩余生命周期**，含端点 fallback、`THINKING_SIGNATURE_INVALID` 重试、内容过滤重试、账号重试、再次 hold/release。只豁免一次 attempt 会让内部第二个端点重试落回 200s，行为取决于内部重试边界，既脆弱又不可解释。

**代价诚实标注**：上游若连第一个原始 chunk 都永不给，Layer C 不再终结它，最终靠客户端取消 / idle watchdog / AbortSignal / 连接断开兜底。这与「hold 阶段不由 stream watchdog 治理」这条裁决一致。

**接线事实**（推翻了语义检索给出的「3 callers」表象）：`wrapStreamWithStallDetection` 源码级生产调用**只有一处** `kiroApi.ts:2818`；上游是两处 `parseEventStream` 调用（`:2427` 主路径、`:2560` thinking-signature 重试）。

**代价**：7 个签名变更、5 个转发边界。侦察明确否掉了 AsyncLocalStorage / 模块全局 / 给 `AbortSignal` 挂私有字段 / WeakSet 这些「省参数」方案 —— 它们把并发请求隔离与重试生命周期变成环境隐式状态，风险高于 7 个显式签名。

**§0.18 错路质疑自查**：3 层但**相邻**（proxyServer → kiroApi → streamWatchdog 是一条直链），非「≥3 个不相邻层」；新增内容的理由是「该请求来自 hold 放行」这个事实全仓不存在、必须新流转，不是上游形状错误。→ 不触发错路，继续。

**`holdConfig.ts` 清理裁决**：删掉 `LAYER_C_FIRST_CHUNK_TIMEOUT_MS_ASSUMED`、`LAYER_C_SAFETY_RATIO`、过期注释与 warning 块。**明确不从 `holdConfig.ts` import `STREAM_FIRST_CHUNK_TIMEOUT_MS`** —— 豁免落地后归一化不再需要比较这两个时间值，导入只会造一个无业务用途的跨模块依赖。SSOT 继续留在 `streamWatchdog.ts:83`。
